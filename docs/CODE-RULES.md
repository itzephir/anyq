# Правила кода

Эти правила обязательны для реализации и ревью anyq. Проверки CI дополняют ревью: они не доказывают SOLID, DRY или качество границ автоматически.

## Один тип на файл

Один самостоятельный `struct`, `enum` или `trait` — один файл. Правило распространяется на entities, value objects, DTO, интерфейсы, интеракторы, адаптеры, CLI arguments и test doubles. Реализации и вспомогательные функции, обслуживающие этот тип, находятся рядом с ним. Функционально локальные вложенные типы допустимы; помещение независимых типов в inline module не считается вложенным классом. `lib.rs`/`mod.rs` задают явные модули и exports, без объявлений типов.

## Читаемость и пустые строки

Разделять одной пустой строкой объявления, impl-блоки и методы. Внутри функций отделять логические этапы: проверку входа, чтение состояния, изменение, сохранение и возврат результата. Связанные действия остаются одной группой; пустая строка после каждого выражения не нужна.

В тестах визуально отделять подготовку данных, проверяемое действие и утверждения. Imports, атрибуты и комментарии должны сохранять понятную связь со своим объявлением. Это часть ручного оформления кода: Rustfmt сохраняет формат, но сам не выделяет смысловые блоки.

## Ответственность и зависимости

- **SRP:** один тип имеет одну предметную или техническую ответственность. `ClaimDeliveryInteractor` отвечает за выдачу, `CompleteDeliveryInteractor` — за завершение и атомарный следующий этап. Нельзя собирать их в общий manager/dispatcher.
- **OCP:** новый сценарий получает свой контракт и реализацию, а не новую ветку универсального бизнес-switch. Маршрутизация синтаксиса CLI остаётся во внешнем адаптере.
- **LSP:** адаптеры выполняют полный контракт порта, включая ошибки и rollback. Fake и SQL adapter проходят содержательные сценарии; тесты не ослабляют инварианты.
- **ISP:** потребитель зависит только от нужных сценариев. Worker получает захват, продление, завершение, возврат и чтение топика. Он не получает публикацию, создание групп и остальные операции «на всякий случай».
- **DIP:** домен и интеракторы зависят от своих контрактов. SQL, Win32, POSIX, CLI и framework types остаются снаружи. Выходные порты принадлежат потребителю, зависимости передаются явно через constructors/factories.

Запрещён универсальный бизнес-контракт `execute(Command) -> Output`: он скрывает зависимости, объединяет ответственности и подменяет типизированный результат runtime-разбором. Сценарий возвращает конкретный доменный результат. Например, `ClaimDelivery::claim(Claim) -> Result<Option<Assignment>>` и `CompleteDelivery::complete(CompleteDeliveryRequest) -> Result<Completion>` — независимые контракты.

Composition root может хранить явно созданные handles сценариев в структуре без бизнес-поведения. Такая структура не имеет `execute`, string lookup, скрытого DI или глобального состояния. `UnitOfWork` объединяет только техническую границу одной транзакции и явные persistence-порты; бизнес-сценарии остаются отдельными.

## DRY и KISS

У доменного правила один владелец. Lease/fencing и переходы состояния определяет `Delivery`; публикацию внутри транзакции и восстановление истёкших leases сценарии используют повторно. Нельзя копировать проверки в CLI или SQL и затем независимо исправлять несколько версий.

Не создавать абстракцию без конкретного правила или потребителя. Не вводить универсальную command bus, framework, registry или «настраиваемый» слой ради нескольких простых вызовов. Сохранять прямые типизированные связи, понятные имена и простые ошибки. Совпадение нескольких строк технического кода само по себе не требует общей продуктовой абстракции.

## Границы фич и детали IO

Межфичевые связи идут только через публичный `api`. `api` и внутренние сценарии не импортируют `impl` и SDK. Только перечисленные в [ARCHITECTURE.md](ARCHITECTURE.md) composition roots собирают фабрики реализаций. Контроллеры переводят вход, presenters — результат; продуктовые правила и смысл фильтров принадлежат домену/интерактору. DB adapter выполняет заданные фильтры и транзакции, process adapter запускает и останавливает процессы.

## Проверки

CI на Linux, macOS и Windows проверяет:

- Rustfmt — форматирование Rust.
- Clippy с `-D warnings` — предупреждения и стандартные проверки Rust.
- AST-линтер `anyq-architecture-lint` — один самостоятельный тип на файл, отсутствие типов в entry points и универсального business dispatcher. Отрицательные fixtures подтверждают, что нарушения отклоняются.
- `check_architecture.py` — разрешённый Cargo graph, API/impl boundaries, inward dependencies, выделенные roots и отсутствие IO во внутренних слоях.
- Ruff — lint и форматирование Python tooling/demo.
- Unit/integration tests, строгую OpenSpec validation и переносимый demo.

Не отключать проверку, не исключать неудобный файл и не добавлять blanket allow ради прохождения CI. Узкое техническое исключение, например FFI в Windows process adapter, должно иметь конкретную причину и описание корректности. SRP, SOLID, DRY и KISS дополнительно проверяются по фактическим обязанностям типов и направлению зависимостей при ревью.
