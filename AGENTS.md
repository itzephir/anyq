# Работа над anyq

- Проект — локальная очередь допуска на Rust; спецификация и задачи в OpenSpec. Именованная задача атомарно получает по одному слоту всех своих топиков и удерживает их до явного complete.
- Применять [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md): Clean Architecture Роберта Мартина, сначала доменные фичи, затем слои. Каждая фича имеет отдельные Cargo crates api/impl; межфичевые зависимости только на api.
- Домен владеет переходами Task, инвариантами допуска и смыслом фильтров; интерактор передаёт конкретный фильтр порту. SQLite выполняет IO и преобразования без предметных решений. Команды выполняет вызывающая сторона, а не anyq.
- Порядок регистрации задачи един для всех её топиков. Частичного захвата нет. Выход wait и авария вызывающего процесса не освобождают владение; автоматического таймаута владения нет. Wait без топиков и обычный complete до запуска — ошибки; --force завершает также registered/queued.
- Один самостоятельный тип — один файл: struct, enum и trait в Rust, включая DTO и test doubles. Связанные impl и локальные вложенные вспомогательные типы остаются с владельцем; lib.rs/mod.rs служат явными entry points.
- Разделять пустыми строками объявления, impl-блоки, методы и логические этапы внутри функций. Группировать связанные действия; в тестах визуально отделять подготовку, действие и проверки. Не превращать код в сплошной блок и не ставить пустую строку после каждой строки. Rustfmt не заменяет осмысленную группировку.
- Соблюдать SRP, SOLID, DRY и KISS. Сценарии имеют отдельные типизированные входные контракты и интеракторы. Запрещены универсальные бизнес-API вида execute(Command) -> Output, god objects и зависимости на ненужные потребителю сценарии. Общий transaction boundary допустим для атомарности; он не заменяет контракты сценариев.
- Внутренние crates не используют IO/SDK/SQL/CLI. Порты принадлежат потребителю, реализации явно передаются через constructors/factories. Только перечисленные composition roots собирают impl. Service locator запрещён.
- Обязательные правила кода и примеры: [docs/CODE-RULES.md](docs/CODE-RULES.md). Применять при реализации и ревью; исправлять причину нарушения, не добавлять подавление линтера ради зелёного CI.
- Перед коммитом: cargo fmt --all --check; cargo clippy --workspace --all-targets --all-features --locked -- -D warnings; cargo test --workspace --locked; cargo test --locked -p anyq --test interruptions --features integration-test-hooks; cargo run --locked -p anyq-architecture-lint; python tooling/check_architecture.py; python -m ruff check .; python -m ruff format --check .; npm run spec:check; git diff --check. В CI lint запускается только на Linux; сборка и тесты — на Linux/macOS/Windows. Native Ctrl+C suite обязателен на всех трёх ОС, без skip/ignore.
- Общая схема имён tasks/topics, нормализация кавычек и AutoCreatePolicy принадлежат queue domain. Канонические имена при restore не разбираются повторно. Config domain владеет task.autocreate/topic.autocreate (default false) и db.path. Неуспешный сценарий откатывает свои автоматические создания. Семантика прерываний — docs/INTERRUPTIONS.md.
- Команды gh с сетью/авторизацией/Keychain выполнять вне sandbox. Не просить повторную авторизацию на основании ошибки внутри sandbox.
- Первичный bootstrap допускается в main; следующие изменения через codex/* и PR, без merge по собственной инициативе.
- Default branch защищена: PR, актуальный CI passed от GitHub Actions, без force push/удаления и admin bypass. Конфигурация — .github/branch-protection.json, категории CI — docs/CI.md. Не отключать защиту ради слияния.
- Не отмечать непроверенные tasks завершёнными и не переносить незавершённое поведение в базовые specs. Пользовательский запрос на реализацию разрешает полный workflow OpenSpec, включая инициализацию в новом проекте.
