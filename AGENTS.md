# Working on anyq

- Write repository content in English: documentation, specifications, instructions, code comments, and new contributor-facing text. The CLI is English-only and must not add language selection or translations. Websites and other graphical interfaces support English (`en`) and Russian (`ru`). Russian is allowed in graphical-interface localization resources and language-specific test fixtures. For websites, resolve language from a valid URL override, saved choice, browser preferences, then English; expose it through the HTML `lang` attribute for layout and accessibility.

- The project is a local admission queue written in Rust; specifications and tasks live in OpenSpec. A named task atomically acquires one slot from every attached topic and holds them until explicit complete.
- Follow [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md): Robert Martin's Clean Architecture, organized by domain feature first, then layer. Each feature has separate api/impl Cargo crates; cross-feature dependencies may target api only.
- The domain owns Task transitions, admission invariants, and filter semantics; the interactor passes an exact filter to the port. SQLite performs IO and conversion without making domain decisions. The caller executes commands; anyq does not.
- A task has the same registration order across all its topics. Partial acquisition is forbidden. Returning from wait or a caller crash does not release ownership; ownership has no automatic timeout. Wait without topics and ordinary complete before admission are errors; --force also completes registered/queued tasks.
- One standalone type per file: Rust structs, enums, and traits, including DTOs and test doubles. Related impls and function-local helper types stay with their owner; lib.rs/mod.rs are explicit entry points.
- Separate declarations, impl blocks, methods, and logical phases inside functions with blank lines. Group related actions; visually separate arrange, act, and assert in tests. Avoid solid walls of code and blank lines after every line. Rustfmt does not replace meaningful grouping.
- Follow SRP, SOLID, DRY, and KISS. Use cases have separate typed input contracts and interactors. Generic business APIs such as execute(Command) -> Output, god objects, and dependencies on use cases the consumer does not need are forbidden. A shared transaction boundary is allowed for atomicity; it does not replace use-case contracts.
- Inner crates do not use IO/SDK/SQL/CLI. Ports belong to the consumer; implementations are injected explicitly through constructors/factories. Only the listed composition roots assemble impls. Service locators are forbidden.
- Mandatory code rules and examples: [docs/CODE-RULES.md](docs/CODE-RULES.md). Apply them during implementation and review; fix the cause of violations rather than suppressing a linter to make CI pass.
- Every behavior change requires integration coverage at its real external boundary. UI changes also require native screenshot regression scenarios with reviewed PNG golden files tracked in the repository. Run applicable integration and screenshot scenarios on Linux, macOS, and Windows; missing goldens or visual regressions must fail CI. Unit tests, mocks, package builds, and ad hoc screenshots do not replace these checks. Golden updates must be explicit and reviewable, never automatically accepted by the comparison job.
- Before committing: cargo fmt --all --check; cargo clippy --workspace --all-targets --all-features --locked -- -D warnings; cargo test --workspace --locked; cargo test --locked -p anyq --test interruptions --features integration-test-hooks; cargo run --locked -p anyq-architecture-lint; python tooling/check_architecture.py; python -m ruff check .; python -m ruff format --check .; npm run spec:check; git diff --check. CI runs lint on Linux only; builds and tests run on Linux/macOS/Windows. The native Ctrl+C suite is mandatory on all three operating systems, without skip/ignore.
- Shared task/topic naming rules, quote normalization, and AutoCreatePolicy belong to the queue domain. Restore does not parse canonical names again. The config domain owns task.autocreate/topic.autocreate (default false), task.autostart (default true), and db.path. Topic.autostart overrides the task default; --stop persists until explicit start. Wait only observes running, ordinary start requires immediate admission, and start -w waits for it. Failed use cases roll back their automatic creations. Interruption semantics are in docs/INTERRUPTIONS.md.
- Run gh commands requiring network/authentication/Keychain access outside the sandbox. Do not request reauthentication based on an error inside the sandbox.
- Initial bootstrap may use main; subsequent changes use codex/* branches and PRs. Do not merge on your own initiative.
- The default branch is protected: PRs and a current CI passed check from GitHub Actions are required; no force pushes, deletion, or admin bypass. Configuration: .github/branch-protection.json; CI categories: docs/CI.md. Do not disable protection to merge.
- Do not mark unverified tasks complete or move unfinished behavior into baseline specs. A user request for implementation authorizes the full OpenSpec workflow, including initialization in a new project.
