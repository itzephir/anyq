## MODIFIED Requirements

### Requirement: Атомарная регистрация с топиками
`anyq task create NAME --topic TOPIC` и краткая форма `-t TOPIC` SHALL регистрировать задачу и связывать её с существующим топиком в одной транзакции с автоматическим допуском после сохранения всех связей. Флаг SHALL допускать повторение для нескольких топиков; повтор одной связи SHALL быть идемпотентным. Результат с топиками SHALL иметь состояние running при разрешённом автоматическом запуске и полном допуске, иначе queued. Ошибка проверки или сохранения SHALL не оставлять задачу или часть связей.

#### Scenario: Несколько начальных топиков
- **WHEN** вызывается task create my-task --topic cpu -t repo -t cpu
- **THEN** создаётся одна задача с двумя связями cpu и repo; при свободных ресурсах она сразу running и занимает по одному слоту обоих топиков

#### Scenario: Неизвестный начальный топик
- **WHEN** хотя бы один указанный при регистрации топик не существует и topic.autocreate выключен
- **THEN** команда возвращает ошибку, а новое имя задачи и связи не сохраняются

### Requirement: Членство задачи в нескольких топиках
`anyq topic link TOPIC NAME` и `anyq task link NAME TOPIC` SHALL равнозначно добавлять существующую задачу в существующий топик, переводя registered в queued и автоматически проверяя допуск всех queued-задач, через один сценарий AddTaskToTopic. Одна задача SHALL поддерживать несколько разных топиков. Повтор той же связи queued-задачи SHALL быть идемпотентным; членство running- и completed-задач SHALL не изменяться.

#### Scenario: Равнозначные формы link
- **WHEN** при занятом cpu связь создана через topic link cpu my-task и повторена через task link my-task cpu
- **THEN** сохраняется одна queued-связь без захвата слота, а обе команды сообщают `successfully added 'my-task' to topic 'cpu'`

#### Scenario: Два ресурса
- **WHEN** при занятых ресурсах my-task добавляется в itzdesign-commands и itzdesign-repo-lock
- **THEN** обе связи сохраняются без захвата слотов, а CLI для каждой сообщает `successfully added 'my-task' to topic 'TOPIC'`

#### Scenario: Неизвестная задача или топик
- **WHEN** команда добавления ссылается на отсутствующее имя задачи или топика
- **THEN** CLI возвращает ошибку без создания неявной задачи или топика

#### Scenario: Добавление во время выполнения
- **WHEN** задаче в состоянии running добавляют ещё один топик
- **THEN** команда отклоняется, а набор занятых ресурсов сохраняется

### Requirement: Блокирующее ожидание собственного допуска
`anyq task wait NAME` SHALL ожидать допуск указанной queued-задачи и возвращать код 0 только после её перехода в running. Running SHALL немедленно давать успех; неизвестная задача, отсутствие топиков и completed SHALL давать ошибку без ожидания. Wait SHALL только наблюдать состояние, не выполнять допуск и не менять владение. Ожидание SHALL не запускать команды или отдельного исполнителя задач.

#### Scenario: Нет топиков
- **WHEN** wait вызывается для зарегистрированной задачи без топиков
- **THEN** CLI немедленно сообщает ошибку `'my-task' is not registered in any topic` и возвращает ненулевой код

#### Scenario: Занятый ресурс
- **WHEN** у queued-задачи ещё нет допуска по всем её топикам
- **THEN** CLI сообщает `waiting for 'my-task' to start` и продолжает ожидание

#### Scenario: Допуск получен
- **WHEN** задача атомарно получает допуск во всех топиках
- **THEN** wait возвращает код 0, после чего вызывающая сторона сама выполняет внешнюю работу

#### Scenario: Два ожидания одного имени
- **WHEN** два процесса одновременно вызывают wait для одной задачи
- **THEN** оба получают успех после одного и того же перехода задачи в running; повторный wait также успешен

### Requirement: Обычное завершение запущенной задачи
`anyq task complete NAME` SHALL завершать только running-задачу, атомарно переводя её в completed и освобождая все её слоты и автоматически допуская следующие доступные задачи в той же транзакции. Зарегистрированная или queued-задача SHALL давать ошибку `'NAME' was not run`. Неизвестная или уже завершённая задача SHALL давать ошибку без изменения состояния.

#### Scenario: Завершение
- **WHEN** complete вызывается для running-задачи my-task
- **THEN** CLI сообщает `'my-task' successfully completed`, а прежнее владение освобождено, а следующие доступные queued-задачи уже running без вызова wait

#### Scenario: Задача не запускалась
- **WHEN** complete вызывается для registered- или queued-задачи my-task без --force
- **THEN** CLI сообщает `'my-task' was not run`, возвращает ненулевой код и сохраняет состояние

### Requirement: Принудительное завершение
`anyq task complete --force NAME` и краткая форма `-f` SHALL позволять переход registered-, queued- и running-задачи в completed. Для незапущенной задачи операция SHALL снимать её с очередей без исполнения внешней работы; для running-задачи SHALL освобождать все её слоты. Отсутствующее имя SHALL создаваться только при включённом task.autocreate; completed SHALL не перезапускаться. Снятие предшественника SHALL автоматически допускать ставшие доступными задачи в той же транзакции.

#### Scenario: Незапущенная задача
- **WHEN** complete --force вызывается для queued-задачи my-task
- **THEN** CLI сообщает `'my-task' successfully completed`, задача становится completed и перестаёт блокировать очереди

#### Scenario: Force во время ожидания
- **WHEN** задача завершена с --force раньше получения допуска ожидающим wait
- **THEN** ожидающий wait возвращает ошибку без разрешения выполнять внешнюю работу

### Requirement: Доменные имена задач и топиков
Общая политика domain SHALL требовать ASCII Latin initial для bare-имени и разрешать любой хвост. Bare list/create/capacity/link/add/start/autostart/wait/complete/config/help SHALL быть запрещены. Одна буквальная внешняя пара обратных кавычек SHALL разрешать любое содержимое, включая пустое, команды и начальные дефисы, и сниматься ровно один раз. CLI и SQL SHALL не копировать правила.

#### Scenario: Голое запрещённое имя
- **WHEN** Topic или Task создаются с bare create, --cpu или нелатинским началом
- **THEN** domain отклоняет имя без изменения агрегата

#### Scenario: Произвольное quoted-имя
- **WHEN** имя целиком обёрнуто буквальными обратными кавычками
- **THEN** допускаются любые внутренние символы, команды и пустое содержимое

## ADDED Requirements

### Requirement: Автоматическое продвижение очереди
Успешные регистрация с топиками, link, complete (включая force), изменение capacity и autostart топика SHALL до commit допускать все доступные queued-задачи с разрешённым автозапуском по общему порядку регистрации. Допуск SHALL сохраняться атомарно с исходным изменением. Активный wait или фоновый процесс SHALL не требоваться; ошибка сохранения SHALL откатывать всю операцию.

#### Scenario: Освобождение без наблюдателя
- **WHEN** владелец единственного слота завершается, а следующий queued не имеет активного wait
- **THEN** завершение сохраняет владельца completed и следующую задачу running одной транзакцией

#### Scenario: Увеличение capacity
- **WHEN** capacity занятого топика увеличивается с одного до трёх и три задачи ждут его слот
- **THEN** две самые ранние доступные задачи становятся running, третья остаётся queued

#### Scenario: Снятие блокирующего предшественника
- **WHEN** force снимает раннюю queued-задачу, которая блокировала более позднюю на свободном топике из-за другого занятого ресурса
- **THEN** поздняя задача получает полный допуск без wait

#### Scenario: Независимые ресурсы
- **WHEN** ранняя задача ждёт занятый топик, а поздняя требует только другого свободного топика
- **THEN** поздняя задача становится running, ранняя сохраняется queued без частичного захвата

#### Scenario: Уже запущенная задача
- **WHEN** wait вызывается для running-задачи один раз или повторно
- **THEN** каждый вызов немедленно возвращает 0 без изменения задачи и слотов

### Requirement: Атомарное пакетное связывание
`anyq topic link TOPIC NAME...` SHALL связывать одну или несколько задач с топиком, а `anyq task link NAME TOPIC...` SHALL связывать задачу с одним или несколькими топиками. Пачка SHALL сохраняться целиком до автоматического допуска. Ошибка любого имени, перехода или записи SHALL откатывать все связи и autocreate. Дубликаты SHALL не создавать повторных связей. Name-first формы SHALL быть равнозначны.

#### Scenario: Несколько ресурсов одной задачи
- **WHEN** task link build cpu repo выполняется при свободных cpu и repo
- **THEN** обе связи сохраняются вместе, и build получает полный допуск к обоим ресурсам

#### Scenario: Несколько задач одного топика
- **WHEN** topic link cpu third first second связывает зарегистрированные first, second, third с односместным cpu
- **THEN** все связи сохраняются, first становится running по порядку регистрации, остальные остаются queued

#### Scenario: Ошибка в конце пачки
- **WHEN** последний участник пачки не существует при выключенном autocreate либо уже running
- **THEN** ни одна новая связь пачки не сохраняется и никто не получает новый допуск

#### Scenario: Полная цепочка пачки
- **WHEN** topic link cpu second first -wc выполняется для задач first и second, зарегистрированных в таком порядке
- **THEN** вся пачка сначала сохраняется, затем first и second ожидаются и завершаются по порядку регистрации

### Requirement: Приоритет автоматического запуска
Задача SHALL сохранять default task.autostart при создании. Не настроенный топик SHALL наследовать этот default; `topic TOPIC autostart [on/off]` SHALL задавать приоритетное значение, без аргумента — on. Автозапуск SHALL требовать on у всех топиков задачи и отсутствия явного stop. Изменение настройки топика SHALL атомарно пересматривать queued, не останавливая running.

#### Scenario: Топик важнее default
- **WHEN** default задачи false, но её единственный топик имеет autostart on
- **THEN** при доступных ресурсах задача автоматически становится running

#### Scenario: Один запрещающий топик
- **WHEN** хотя бы один топик задачи имеет autostart off
- **THEN** автоматический допуск не выполняется; явный start всё ещё возможен по общим правилам ресурсов и очереди

### Requirement: Управление запуском при регистрации
Create SHALL принимать взаимоисключающие --start, --stop и -s. Stop SHALL сохранять запрет автоматического запуска до явного start. Start при разрешённом автозапуске SHALL ничего дополнительно не делать, иначе SHALL требовать немедленного полного допуска с rollback регистрации при отказе. -s SHALL инвертировать эффективное разрешение. Кластер -tswc TOPIC SHALL сохранять смысл отдельных флагов.

#### Scenario: Постоянный stop
- **WHEN** задача создана с --stop и затем ресурсы освобождаются или включается autostart топика
- **THEN** она остаётся queued до явного task start

#### Scenario: Кластер при включённом автозапуске
- **WHEN** create NAME -tswc TOPIC выполняется при autostart on
- **THEN** задача сохраняется stopped/queued, цепочка ждёт отдельного start и после наблюдения running завершает задачу

#### Scenario: Кластер при выключённом автозапуске
- **WHEN** create NAME -tswc TOPIC выполняется при autostart off и свободном слоте
- **THEN** задача немедленно запускается, wait наблюдает running, complete завершает её

### Requirement: Явный запуск и его цепочки
`task start NAME` и `task NAME start` SHALL немедленно пытаться получить полный допуск независимо от автозапуска; при недоступных ресурсах или месте в очереди CLI SHALL возвращать ошибку без изменений. -w/--wait SHALL повторять попытки до допуска; -c/--complete SHALL требовать wait и затем завершать задачу. Running SHALL сообщать already running с успехом; registered без топиков и completed SHALL давать ошибку.

#### Scenario: Занятый ресурс
- **WHEN** start без -w вызывается для queued-задачи с недоступным топиком
- **THEN** команда возвращает ошибку, сохраняя queued и нулевое частичное владение

#### Scenario: Ожидающий явный запуск
- **WHEN** task NAME start -wc ждёт ресурс и владелец освобождает его
- **THEN** задача получает все слоты, затем завершается; ресурсы освобождены либо переданы следующим доступным задачам

### Requirement: Обновление поддерживаемой схемы
База версии 2 SHALL обновляться до 3 атомарно, сохраняя имена, регистрацию, связи, состояния и владение. Старые задачи SHALL получать default autostart=true и stopped=false; топики SHALL наследовать default. Открытие базы SHALL не выполнять допуск. Прерывание до commit SHALL сохранять прежнюю схему, после — полную новую.

#### Scenario: Старое владение
- **WHEN** открывается база версии 2 с running-владельцем и queued-последователем
- **THEN** после обновления владелец удерживает прежние слоты, последователь остаётся queued и допускается после явного complete владельца
