# Design

## Context

Мотивация — в proposal.md. До этого изменения queue-api содержал Message/Delivery и контракты публикации, claim, lease и handoff; dispatch выполнял их через Store/UnitOfWork и четыре persistence-порта. SQLite хранил topics, consumer_groups, messages и deliveries в схеме версии 1. Worker был выделен в четыре crates и запускал процессы. CLI имел JSON-презентеры; первый пилот itzdesign использовал внешние run.py/execute.py.

Пользователь подтвердил замену прежнего API, атомарное получение слотов всех топиков и владение до явного complete без heartbeat. Это заменяет старое решение о consumer groups. AGENTS.md и openspec/config.yaml обновлены под новую модель; базовые specs синхронизируются после проверки реализации и разрешённого merge.

## Goals / Non-Goals

**Goals:** нативный CLI допуска к локальным ресурсам; одна долговечная задача и её набор топиков; проверяемая атомарность и явное освобождение; одинаковое поведение на трёх ОС.

**Non-Goals:** запуск и остановка команд, payload-команды, consumer groups, leases, автоматические повторы и следующий этап, DAG зависимостей, демон, удалённые ресурсы, автоматическая конвертация старых сообщений, повторное использование имени завершённой задачи.

## Decisions

### Задача и её состояние

Task — агрегат с уникальным именем в пределах базы, неизменным номером регистрации, состоянием и набором топиков. Topic сохраняет имя и положительную вместимость. Состояния:

- registered: топиков ещё нет;
- queued: есть хотя бы один топик, допуск ещё не получен;
- running: занято по одному слоту всех связанных топиков;
- completed: задача больше не занимает слоты и не участвует в очередях.

Связи и завершённые задачи сохраняются для истории. Повторный task add того же имени — ошибка; повтор добавления той же связи queued-задачи идемпотентен. Running/completed нельзя добавлять в другие топики. Повторный wait для running и повторный complete для completed — ошибки: они не дают второй стороне нового разрешения на выполнение.

RegisterTask принимает отдельный RegisterTaskRequest с именем и списком начальных топиков. Без топиков результат registered, с топиками — queued. Проверка существования топиков, регистрация и сохранение всех связей выполняются в одной транзакции; ошибка не оставляет частично созданной задачи. Переходы и уникальность связей по-прежнему принадлежат Task. Два порядка аргументов link нормализуются в один запрос внешнего CLI и вызывают один AddTaskToTopic.

Альтернатива с отдельными доставками задачи для каждого топика отвергнута: она допускает независимые статусы и частичное владение, которых здесь быть не должно.

### Единый порядок и проверка допуска

Монотонный номер назначается при task add. Для каждого топика вычисляются число running-задач и число queued-задач с меньшим номером регистрации. Свободные слоты равны capacity минус running; задача допускается, когда число её предшественников меньше числа свободных слотов в каждом её топике.

У одной пары задач один порядок во всех общих топиках, даже если связи добавлялись в разной последовательности. Это выбранное правило очереди; порядок по времени добавления каждой отдельной связи создавал бы перекрёстные очереди. Registered без топиков и completed в порядок топика не входят. Queued-задача сохраняет место, даже если её wait ещё не запущен; ненужную задачу снимают через complete --force.

Чистая доменная политика получает состояние задачи и снимки использования ресурсов. Интерактор задаёт фильтры чтения и передаёт данные политике; SQL считает и читает заданные записи, но не решает, кому разрешить запуск.

### Одна транзакция для изменения владения

TryStartTask проверяет актуальные состояние и членство, читает использование и предшественников всех топиков, затем сохраняет running в одной Store transaction. SQLite использует существующий IMMEDIATE transaction boundary. При недоступности хотя бы одного топика изменений нет. Если конкурентный add успел раньше допуска, новый топик включается в проверку; если после перехода в running — add отклоняется.

CompleteTask проверяет допустимость перехода и сохраняет completed в одной транзакции. Использование ресурсов выводится из running-задач и их связей; отдельные изменяемые счётчики слотов не вводятся. Это исключает рассинхронизацию счётчиков и двойное освобождение. Изменение capacity ниже уже занятого числа отклоняется тем же доменным правилом.

Последовательный захват ресурсов, даже с последующим rollback на уровне CLI, отвергнут: между вызовами другие процессы увидели бы частичное владение.

### Нативный wait и внешний исполнитель

CLI вызывает отдельный типизированный TryStartTask до результата Started или ошибки; результат Busy означает короткое ожидание во внешнем слое и повтор. Пауза и IO не попадают в домен и интерактор. Транзакция не удерживается на время ожидания. Порядок и доступность каждый раз перечитываются.

Успешный wait фиксирует running до возврата кода 0. Два wait одного имени не могут оба получить новый допуск. Complete --force может завершить queued-задачу, пока CLI ждёт; следующий опрос видит completed и возвращает ошибку, не выдавая допуск. Временная ошибка SQLite также возвращается вызывающей стороне, а не трактуется как Started.

После возврата wait вызывающая сторона запускает свою команду и отвечает за её остановку и результат. Complete означает окончание владения ресурсами, а не автоматически установленный успех внешней команды. Даже аварийное завершение wait после фиксации running не освобождает слоты. Восстановление — явный complete известного имени после проверки внешней работы.

### API, модули и CLI

Queue остаётся владельцем Task, Topic и политики допуска. Существующие queue api/dispatch/sqlite/composition crates сохраняют направленные внутрь зависимости. Отдельные контракты и интеракторы: RegisterTask, AddTaskToTopic, TryStartTask, CompleteTask и управление топиками. Никакого универсального execute API или отдельной фичи запуска процессов не требуется.

Persistence-порты принадлежат dispatch: задачи и их связи — TaskRecords, топики — TopicRecords, атомарность — Store/UnitOfWork. SQLite адаптеры и явная composition root реализуют эти порты. Каждый самостоятельный тип, включая DTO и doubles, находится в своём файле. Clock допустим для метаданных истории, но время не влияет на владение.

CLI поддерживает task add NAME [--topic TOPIC] [--wait] [--complete], topic link TOPIC NAME, task link NAME TOPIC, task wait, task complete с --force и topic --list. Вместимость изменяется через topic capacity TOPIC N; создание — topic create TOPIC [--capacity N]. Краткие формы: -t, -w, -c для регистрации, -l для списков, -c для вместимости при создании топика и -f для force; --topic/-t допускает повторение. -v и -h соответствуют --version и --help. Прежние topic TOPIC add NAME и topic capacity TOPIC --capacity N отклоняются. Подкоманды разбираются Clap; оба link нормализуются в один запрос только внешнего слоя. Нормальные результаты — понятные текстовые сообщения; ошибки входа и состояния идут в stderr с ненулевым кодом.

Цепочка регистрации остаётся во внешнем CLI: атомарный RegisterTask, затем при --wait блокирующий TryStartTask, затем при --complete обычный CompleteTask. Wait требует хотя бы один topic, complete требует wait; неверные сочетания отклоняются до открытия базы. После успешного wait без complete задача остаётся running. Complete выполняется только после успешного wait; ошибка или принудительное завершение ожидающей задачи прерывают цепочку. Особая пользовательская запись -twc TOPIC нормализуется во внешнем слое так, чтобы -t получил следующий аргумент как топик; значения --db, --topic и разделитель -- сохраняются.

ListTasks возвращает все имена по алфавиту, включая completed, через свой узкий контракт и TaskRecords.task_names. GetTask возвращает агрегат со статусом и всеми сохранёнными связями. GetTopicQueue читает queued и running конкретного топика через точные TaskFilter в одном снимке и объединяет их по номеру регистрации; completed и registered не входят в текущую очередь. GetTopic используется для чтения capacity. Команды просмотра — task NAME, topic TOPIC и topic capacity TOPIC; для имени задачи, совпадающего с подкомандой, используется --, например task -- add. Просмотр не меняет владение и возвращает ошибку для неизвестного имени.

Имена топиков create/capacity/link/help и любой начальный - запрещены осознанно. Политика находится в чистой validate_topic_name внутри queue/api; Topic, Task.add_topic и Task.restore используют её. Сценарии и адаптеры делегируют проверку домену, включая восстановление Topic из SQLite. Разделитель -- не является обходом; отдельной дублирующей проверки в CLI нет. Имена задач сохраняют собственное базовое правило имени.

### Схема и несовместимость

Новая схема версии 2 содержит topics, tasks и task_topics. У tasks отдельный монотонный ключ порядка и уникальное имя; у task_topics уникальная пара задача/топик и внешние ключи. Состояния и связи обновляются в общей транзакции. Индексы поддерживают подсчёт running и выбор queued-предшественников по топику и номеру.

Версию существующей базы читают до любых изменений схемы. Версия 1 отклоняется без преобразования или удаления её таблиц; диагностика объясняет выбор отдельного файла через --db. Неизвестная будущая версия также отклоняется. Автоматическую конвертацию нельзя сделать однозначно: у прежнего сообщения нет пользовательского имени и общего владения несколькими топиками.

Четыре worker crates, их exports, process adapters, process fixtures и неиспользуемые зависимости удаляются. Структурные линтеры и CI сохраняются; Cargo graph меняется на шесть crates: четыре queue, CLI и architecture-lint. Примеры используют прямые task-команды и внешний процесс, без task registry в Python.

## Risks / Trade-offs

- [Вызывающая сторона погибла после допуска] → слоты намеренно остаются занятыми; в документации явная диагностика имени и ручное завершение после проверки внешней работы.
- [Queued-задача без активного wait блокирует более поздние] → это следствие выбранного FIFO; complete --force снимает ненужную задачу без запуска.
- [Головная задача ждёт другой ресурс] → порядок может уменьшать использование свободных слотов; это плата за единый порядок и отсутствие частичного захвата, без скрытого обхода очереди.
- [Частые опросы SQLite] → короткие транзакции и ограниченная пауза во внешнем CLI; демон и механизм уведомлений не добавляются в первую реализацию.
- [Имя известно другому локальному процессу] → API кооперативный, не является границей авторизации; force меняет допустимость перехода, а не предоставляет отдельную системную привилегию.
- [Старая база и пилот несовместимы с новым CLI] → отдельный файл версии 2, сохранённый старый бинарник и прежние данные; переход пилота только после проверок.

## Migration Plan

1. Реализовать новые доменные правила и typed use cases; заменить schema/CLI и удалить worker. Не трогать рабочую базу пилота itzdesign.
2. Обновить unit, SQLite и CLI integration suites, demo, Cargo graph и документы. Подтвердить ошибки из пользовательских примеров и конкуренцию нескольких процессов на трёх ОС.
3. Выпустить проверяемый PR с зелёным CI. Старые сообщения не импортировать и не маркировать именованными задачами автоматически.
4. После реализации испытать нативную последовательность в itzdesign на отдельной базе. Откат использует старый бинарник с его старой базой; схемы не смешиваются.
5. После ревью и разрешённого merge синхронизировать delta specs и архивировать change. command-worker retire удаляет также Purpose этого устаревшего capability; остальные базовые Purpose сохраняются.
